\chapter{Make Reusable Functions}\label{ch:reusableFunctions}

Modern computing systems are hierarchical and modular.
Seldom any developer write code that runs on bare metal.
Instead, we write code on top of myriad other components such as compilers, system
libraries, third-party frameworks, operating systems, firmwares, virtual machines, network
protocols, \textit{etc}.
To give you an idea about that, let us consider a simple C program---"Hello World!"
~\autoref{lst:hello-world}.
To execute it on your laptop, you will need to compile it into machine code,
link it with built-in libraries, load the executable into main memory,
and schedule instructions sequentially for CPU cycles.
To compile the high-level program into machine code, compilers are invoked.
To locate and incorporate the \code{stdio} library needed for the \code{printf} function, linkers
come to the rescue.
To execute, the executable is loaded into the main memory by loaders.
As you can see, although the program has only $5$ lines, vast amount of code in the
underlying systems and components are depended on to fill in the gap between authoring the C code
and executing the program on machine.


Functions are the predominant basic building blocks at each level of the hierarchical software
system.
A complex task should be realized by a function tree (sometimes function graph under certain
circumstances).
Each function should be single-responsibility principle (SRP) compliant---easily understood, used,
and changed.
In this chapter, we are going to go over the most important part when designing and implementing
functions for a complex task.

In all mainstream programming languages, a function has a name, an

\subsection{Function Names}\label{subsec:function-names}

The importance of naming can never be overemphasized.
In a sense, your software is what you name it.
Many books has talked about the best practices of naming ~\cite{Martin-R-2009, Mcconnell.2004}.
I'm not going to repeat.
Instead, I am going to introduce a new term to help clarify the various needs for
function names.
When it comes to the requirements for names, there are multiple angle of views.
For one, a name serves as an identifier, a label, or a bookmark----it should be brief but concise.
For another, a name is a caption, a direction, or a manual---it need be informational and
descriptive.
But briefness and descriptiveness are conflicting requirements.
They cannot be satisfied completely and simultaneously.
A spectrum is formed when emphasis of one aspect
over the other varies and it will be referred to as the 'naming spectrum' for the discussion of
this chapter and the book.
When it comes to designing a function, one should keep this in mind and make conscious trade-offs.
So naming a function is an art of balancing.
In general, descriptiveness is emphasized over briefness in function naming.
But there are also other factors that systematically affect the length of function names.
Many of such factors are of historic reasons.
In Unix/Linux system, for example, library function names tend to be brief, such as \code{umask,
chmod, execve, fork}, \textit{etc}.
Whereas libraries written for high-level programming languages tend to have
formal, full names with no abbreviation.
As a rule-of-thumb, the length of a name should be proportional to its scope---long-living names
should be more informational than concise and vice versa.
A short-lived variable names may have shorter names or even an acronym, \textit{e.g.},
\code{temp}, \code{t}, \code{tmptr}.
A long-living variable, such as a member variable of a class, on the opposite, should have a fully
qualified name, \textit{e.g.}, \code{temperatureOfLivingRoom}.
Also, function names in test code may be lengthier than its production counterpart as clarity
prevails over conciseness in test and that test cases are often combinatorial.

For me, I've seen functions on both end of the spectrum: majority of functions have $0$, $1$, $2$,
parameters and some extremely rare but real-world applications, functions with up to $8$
parameters were created just to make use of a legacy C library.

So what rule should we apply?
My short answer is to use an exponential weighing scheme, namely, for a function
with $N$ parameter,
\begin{equation}
    \mbox{cost}~\sim O(\exp(N)).
\end{equation}
This cost represents a rough estimation for the cost of the development, debugging, and maintaining
the source code.
So instead of putting a hard limit over the size of parameters of functions, we use a significant
weighing scheme to scale the cost up.

Sometimes you may have an urge to create a function with $>2$ arguments.
Please resist the from it and refer to ~\autoref{tbl:arg-shortening-tech} for techniques that may
help you create more beautiful and readable solution.
In the extreme case where you seem to run out of all wit and have to do or die,
you should leave a comment reminding/challenging yourself to revisit it later.


\section{Single Responsibility Principle}\label{sec:function-modularity}

The single responsibility principle (SRP) is applicable to functions as well as to other levels
on the software hierarchy.
When applied to functions, it requires that a function serve exactly one purpose.
Robert C. Martin once said ``A class should have only one reason to change.''~\cite{Martin-R-2003}.
What he said is also true for functions---``A function should have only one reason to change.''
%What if otherwise?

%In practice, one still need to define what oneness means.
%I tend to interpret the oneness as ``A single task''.

We want to elaborate how to make the functions we build comply with SR\@..
Although it is quite ambiguous as to what consists of ``oneness'' in functions,
readability, length, and cohesion are the top $3$  orthogonal measurements of it.
%being modular is among the consensus concerning modularity.
If a lengthy function also lacks simplicity and homogeneity,
chance is that it violates SRP and should be refactored.
Some functions may be long (\textit{e.g.} $> 50$ lines) but consist mostly of lines of similar
structure, it is still considered okay.
Some relatively short functions may be hard to comprehend, \textit{e.g.}, an implementation of
a dynamic programming algorithm.
But it may be argued that it is in compliance with the SRP as its code are highly cohesive.
From this perspective, however, it is a well designed function.
But to some creative developers, they may still find ways to make the implementation to be more
readable by factoring some subtasks out of the main function.
On the opposite, if a function performs sophisticated calculation while making
\code{HTTP} request, its cohesion score would be questionable and should probably be refactored.


However, not all functions with 100+ lines must be broken down to smaller functions.
Conversely, simply breaking a 100-line function to shorter functions does not
produce the desired result, either.
Before refactoring, semantic analysis of the function often sheds light on where to start.
Depending on the result, some tasks manifest themselves.
If there are copy-and-paste duplicates or `soft duplicates' and the duplicate code spans more
than one line, then the duplicate code should certainly
be factored out as a standalone helper function.
If there is a section of code that is intrinsically different, detached from the rest, and poses
such a significant presence that it disrupts the latter,
consider factor it out to a helper function.
Once you get a sense of it, these intrinsically different sections can be easily recognized.
Examples of them include lengthy calculations of auxiliary data,
requests for resources over network, interactions with database, disk IOs, \textit{etc.} in
functions whose main task is beyond what is formerly named.


So far we have ignored the cost of developing and debugging the code when comparing monolithic
vs modular code.
Obese functions seldom come into being from day one.
The history of a function usually undergoes a development process over the course of
months or years---bug fixes, feature additions, edge case handling, \textit{etc}.
As code accumulates, it becomes increasingly difficult for the next person to add to it, to fix
it, or to change its behavior.
Duplicate code in it will exacerbate this process by multiplying the difficulty by a factor of
two or more.

\section{Function tree}\label{sec:functionFamilies}

Give a complicated problem, stuff everything into one function is almost certainly a
bad idea.
should construct a
`function tree'
\footnote{Please note that strictly speaking, recursive functions do not fit in this picture as
it will turn the function tree to a function graph.
But we may apply a special treatment to recursive function(s) and maintain the validity of the
above argument.
For more information, see ~\fullref{ch:recursion}.
} much as the construction of an
expression tree for evaluation\footnote{\url{https://en.wikipedia
.org/wiki/Binary_expression_tree}}.

Your functions should be built upon one another.
Together they tell a complex and complete story, with outlines as well as details at the right place.

The collection of helper functions are arranged in tree-like structure and they are built on top
of each others.
First, each of the helper functions are small and readable.
Secondly, each helper function provides a checkpoint which, when times come for debugging, would
be very helpful in testing and verification.
Last but not least, each with a meaningful name, the helper functions act as navigating signs.
Browsing through them is effortless and reader can easily navigate through them without being lost.

It's a common problem among beginners to stuff all the logic into a monolithic function.
But it is a fairly subtle mistake for intermediate professionals to arbitrarily chop
up a function into pieces to ``promote modularity''.
True modularity comes from coherence and coherence is beautiful.
Much like making the cut of final scores into `A', `B', `C', \textit{etc.}, a skillful programmer
looks for certain signals to determine if a new function (or class) is to break off the main one.
Some of these signals are as follows:

\begin{itemize}
    \item The logic to obtain certain an intermediate value or object obstructs the main flow of
    control
    \item A code snippet whose runtime complexity may be drastically different from the main
    \item A portion of the code need to enter a critical section
    \item Certain portion but not all of the code need error handling as a \code{try .. catch}
    \item A chunk of identical or almost identical code occurs at multiple places
    \item Auxiliary concerns such as counting or logging of certain operations
    \item You find it takes a while to look back at your code a day later
    \item The logic you want to test is hard to test
\end{itemize}

Our world is run on a conglomeration of hierarchical, systems built on top one another, made of
various code of all varieties, large or small, open source and proprietary.
Bugs can hide at all the levels in the hierarchy.
It's truly a miracle that our software world runs at all this very moment.

By creating and assemble single-purposed functions, one promotes code reusability and testability.
More importantly, we constrain the span of variables to a more limited scope and thus
eliminate a lot of possible hiding places for bug.

\section{Idempotence}\label{sec:idempotence}

Especially paying attention to creation
of read-only  \textit{vs.} state-altering functions,
idempotent  \textit{vs.} non-idempotent functions.

Idempotence is an important characteristics of member methods in object-oriented design.
idempotent: denoting an element of a set which is unchanged in value when multiplied or otherwise operated on by itself.

immutable: constant function has no state altering operation whatsoever
idempotent: 1+ call of the function are equivalent to 1 call.
