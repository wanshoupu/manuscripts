\chapter{Organize your Conditional Statements}\label{ch:organizeYourIfElse}

Conditional is a control switching mechanism to alter code execution path,
conditioned by one or more boolean conditions.
Conditional control flow is the most basic programming building blocks in programs
of almost all programming languages.
It may seem strange to you that I am actually spending a full chapter on this as
many books and articles have already given this comprehensive discussions,
\textit{e.g.},
Wikipedia\footnote{\url{https://en.wikipedia.org/wiki/Conditional_(computer_programming)}}.

But just because it is basic and widely discussed does not mean that many people can do it right
or bother their willpower to do it right.
Most of us agree that seldom any implementation of non-trivial logic is
correct and optimal at the first attempt.
But based on my observation working in top-tier tech companies,
it is often
the very first working version with bulging and intertwined logic that makes its way to production
codebase and invoked by millions for real businesses.
It is like a restaurant utensil was used for cooking for many days without being washed and no
one notices.

``As long as it works, why should one bother to simplify the logic?'', you may argue.
I'd like to quote Steve McConnell to respond:
``..the primary audience [of your code] is made up of humans, not computers.''\cite{Mcconnell.2004}.

\begin{quote}
    ``Any fool can write code that a computer can understand.
    Good programmers write code that humans can understand.''\\
    —Martin Fowler
\end{quote}

Intertwined logic, even though it works, are hard to read, understand, debug, and modify.
It fails the primary purpose of communicating to other humans.
Worse, it often results in redundant/duplicate code.

Twisted logic in code often reveals a fierce battle that the author struggles to make something
that works.

I believe every minute spent with the basics is worthwhile before making publish pull requests on
production code.

%Communicate clear, succinct code to colleagues and successors are much more efficient.

In this chapter, I'm going to share my experience of how to polish complicated logic into simple,
beautiful, and succinct code.
out \code{if elseif else} switching statements to reduce redundancy condition checks on the one
hand and duplicate code on the other.

Some of the techniques I employ is of math origin, especially basic Boolean algebra such as logical
equivalences: double negation elimination, De Morgan's laws, distributive law, \textit{etc.}
and normal forms: disjunctive normal form (DNF) or conjunctive normal form (CNF).

Through plenty of examples, I demonstrate how to apply these techniques for logic simplification.
In doing so, I hope programmers would be inspired to the beautiful, succinct conditional statements.

\section{\code{if-else}-condition}\label{sec:if-else-condition}

A boolean variable has two values-\code{true} and \code{false}.
A simple condition in a \code{if-else} test has two execution alternatives-the \code{if}-block or
the \code{else}-block;
A composite condition of two boolean variables and a logical connective, such as
\code{or}/\code{and}, may have up to 4 alternatives;
and so on.

But when disguised in real problems, especially when some alternatives are omitted or no-op,
optimal coding may not be so straightforward.
Show in ~\autoref{lst:nestedBranching} is my own code.

I decided to eliminate the nested conditional statements first.
Observing that the \code{else} block of \code{if (condition1)} is much simpler, I decided to flip
the logic by negating \code{condition1}.

Then I promoted the nested \code{if (condition2)} up to the first-level so that overall they
become sequential conditional statements comprised of \code{if\{..\}else if\{..\}else\{\}} blocks
that are built on top of one another.
The resulting code is as shown in\autoref{lst:simpleBranching}.

caption={Equivalent code snippet as ~\autoref{lst:nestedBranching} with simple condition checking
}]{if-else/composite_condition_simplified1.java}

Now the conditional statements are streamlined and can be understood at a glance.
Comparing with ~\autoref{lst:nestedBranching}, it is a big improvement.

But still it has duplication code.

So I found a piece of paper and for each of the three statements, I wrote down the condition to
be satisfied in order for it to be executed.
My table is shown in ~\autoref{tbl:breakdown-of-conditions}.
Clearly simplifying the condition for the execution of \code{statement2} is the key and let us do
the math now.
Let $c$ be the condition for \code{statement2} to be executed and
\begin{align*}
    a &= \text{\code{condition1}}, \\
    b &= \text{\code{condition2}}. \\
\end{align*}
Then
\begin{align}
    c &= a \land \lnot b \lor \lnot a  \nonumber \\
    &= a \land \lnot b \lor (\lnot a \land \lnot b \lor \lnot a \nonumber) & \text{// absorption law
    }\\
    &= (a \land \lnot b \lor \lnot a \land \lnot b) \lor \lnot a \nonumber & \text{// associativity
    law}\\
    &= \lnot b \lor \lnot a & \text{// distributivity law} \nonumber \\
    &=\lnot (a \land b) & \text{// De Morgan's law} \label{eq:boolean-expression-simplify}
\end{align}

~\autoref{eq:boolean-expression-simplify} shows that the condition of execution for
\code{statement2} is \code{!(condition1 && condition2)} and this can be an \code{else} clause of
\code{if (condition1 && condition2)} which is the condition for the execution of \code{statement1}.

With this piece of wit, it is straightforward to implement much simple code such as
~\autoref{lst:final-simplified-conditional-statement}.

\lstinputlisting[label={lst:final-simplified-conditional-statement}, caption={Simplified logic that
is equivalent to ~\autoref{lst:nestedBranching}}]{if-else/composite_condition_simplified2.java}

Of course the above process is not the only process to simplify logic.
Another possible way to achieve this is to use truth table.
let's look at this in detail.

\begin{table}[h]
    \begin{center}
        \caption{True value table for \code{condition1} and \code{condition2}.
        \label{tbl:true-value-table}}
        \begin{tabular}{|c|c|c|}
            \hline
            \code{condition1} & \code{condition2} & execution \\
            \hline
            \code{false} & \code{false} & \code{statement2}\\
            \code{false} & \code{true} & \code{statement2}\\
            \code{true} & \code{false} & \code{statement2}, \code{statement3}\\
            \code{true} & \code{true} & \code{statement1}, \code{statement3}\\
            \hline
        \end{tabular}
    \end{center}
\end{table}

I constructed truth table as ~\autoref{tbl:true-value-table}.
Since there are two conditional variables \code{condition1} and \code{condition2}, there are
total four entries in the table.
The third column shows the statements executed if the condition of the entry is true.

Now we can summarize the table and arrive at the following conclusions
\begin{enumerate}[label={\roman*:}]
    \item \code{statement1} is executed iff both \code{true};
    \item \code{statement2} is executed iff not both \code{true};
    \item \code{statement3} is executed iff \code{condition1=true}, regardless of
    \code{condition2}.
\end{enumerate}

With these in mind, implementation of something like
~\autoref{lst:final-simplified-conditional-statement} naturally follows.

So here two simplifying logic processes are presented.
In practice, one may find one out of the two to be more useful under certain circumstances.
So one may try one or the other or both, depending on which one is more convenient.

\section{Build up your cases in \code{if}-stack}

One frequently faces need of multi-way switching.
One can realize this with nested \code{if..else} statements like ~\autoref{lst:nested_if_else}.
\lstinputlisting[label={lst:nested_if_else}]{if-else/nested_if_else.java}
The nesting level will go deeper with more switching fanouts and
the logic becomes unwieldy pretty quickly.
As an alterative with boosted readability, one can organize multi-way switching with an
\code{if}-stack.
A \code{if}-stack refers to a stack of \code{if}, \code{else if} (\code{elif} for \python), or
\code{else}.
For example the ~\autoref{lst:nested_if_else} complexity can be equivalently written as
\lstinputlisting[label={lst:if-stack}]{if-else/if_else.java}
Sometimes a \code{switch}-statement may be equivalently used in place of a \code{if}-stack on
limited use cases.
But we are going to limit our discussion to \code{if}-statement for now.

The execution of an \code{if}-stack is like walking up a staircase---one
builds up cases by successive tests in a step-by-step fashion.
The conditional expression of the leading \code{if}-clause is the first step of check.
If it is evaluated to \code{true}, then the \code{if}-clause is executed
and the rest of the stack is skipped.
Otherwise, the conditional expression of the next branching clause is evaluated
and so on until the end of the \code{if}-stack.
Note that \code{if}-stack may not be in the form of \code{if..else if..else}.
With the presence of \code{return} and \code{break}, a series of \code{if}-statements can also
form an \code{if}-stack.

When taken apart, the conditional expressions of \code{if}-stack
are cumulative---a later case combines all earlier conditionals with its own.
For example the ~\autoref{lst:if-stack}, if taken apart, will be
\lstinputlisting[label={lst:if-stack-taken-apart}]{if-else/if_stack_taken_apart.java}
Note that the three \code{if}-blocks are totally independent and
the order among them does not matter any more.
Apart from this ordering flexibility, the code readability and
the performance of ~\autoref{lst:if-stack-taken-apart} is
generally speaking worse than ~\autoref{lst:if-stack} as it does a significant amount of
redundant tests.
When inspecting code for logic fallacies and unfounded assumptions, for example, one has to keep
this cumulative effect in mind: all the assumptions about the
the current line of code should have been tested by exactly one of the conditionals ahead.
A missing test will likely result in exception.
From this perspective, the alternative form ~\autoref{lst:if-stack-taken-apart} may be more
straightforward to spot untested assumptions made for a later case than its \code{if}-stack
counterpart.

As an example of \code{if}-stack, let's consider the implementation of method \code{equals(Object
obj)} as shown in ~\autoref{lst:if-stack-equals}.
The first test we do is the nullity of the argument.
If it is not null, then we test if its of type \code{MyClass}.
Only if it is not null and is of type \code{MyClass}, we cast it to type \code{MyClass}
and test equality between member variables of
\code{this} instance and \code{that} instance, pairwise.
From this example, you see how we build up the cases like a staircase step-by-step cumulatively.
\lstinputlisting[label={lst:if-stack-equals},
caption={Example implementation overriding\code{equals}in a subclass}]
{if-else/equals.java}

As another example, let us consider the code for determining the lowest common ancestor
of two values in a binary search tree.
This is a typical problem where the cases to be tested can be combinatorial
if not handled properly, your code can blow out like crazy.
But if we design our \code{if}-stack properly, a couple of lines of code can handle all the
combinations like a breeze.
Take a look at ~\autoref{lst:if-stack-lca}.
The cases are built from ground up:
\begin{enumerate}
    \item Test nullity;
    \item Test for left branching;
    \item Test for right branching;
    \item Test for existence of keys;
    \item Final case;
\end{enumerate}
Note later statements are built on the assertions of previous tests---test for left/right
branching requires the non-null attributes of root otherwise the code will throw
\code{NullPointerException}.
Also note that as the cases are being built up, the solution spaces are also being ruled
out---each time we eliminate a half-space with a test---much like that of a binary search.
\lstinputlisting[label={lst:if-stack-lca},
caption={An implementation of finding lowest common ancestor in a binary search tree.}]
{if-else/lca.java}
Some source states that when designing \code{if}-stack do the simple tests first.
I think that's a superfluous observation.
The underlying rule is to do the most informative test first.
That way, the solution space would be squashed at the earliest possible time.
Building up the cases of an \code{if}-stack is ultimately empirical.
Even the experienced developers may have to make a couple of attempts to get it right.
