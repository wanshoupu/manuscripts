\chapter{Flatten Nested Loops} \label{ch:loop-thinning}

Nested loops are a complexity nuance that is hard to understand.
Sometimes can cause bloated runtime complexity, \textit{e.g.} what could be $O(N)$ would be
$O(N^2)$ .
Programming loops is a complex work.
First working version is seldom the best solution.
This chapter is a spinoff of the ~\autoref{ch:loops}.
We spend this chapter for the sole purpose of simplifying nested loops.
The rule of thumb is ``avoid nested loops'.
If nested loops can be simplified to one-layer loop, by using auxiliary data structures, better
algorithm, and so on, that will be the first choice.
Otherwise, refactoring the code may be necessary to decouple subtasks from the main one.
One may raise counter examples, say, iterating through $2$D array elements using indexes \code{i,j}.
I would argue back that refactoring the inner index access into a separate function may still be
a better choice as it makes the inner loop more meaningful with a separate function with a
meaningful name.
Some one may argue about performance, saying that function call has overhead especially made in a
loop.
My answer to that is that ``By that argument you do not really care about performance.''
Because if you really care about performance you would have vectorized your code using matrix
operations instead of using nested loops.

\section{Conclusion}

Nested loops are hard to understand and are generally considered unacceptable in production code.
They should be avoided if at all possible.
With the `loop thinning' technique discussed in this chapter, many cases of nested loops can be
compactify and converted to simple loop.
If this is not possible or the resulting code is even harder to understand, one should consider
refactor nested loop into smaller functions.
