\chapter{Construct Lean Loops} \label{ch:loops}

As one of the most widely used building block, loop is a programing productivity amplifier---with
a static body and some nominal overheads (\textit{e.g.}, loop variables,
which are used to register loop state), a loop can be executed as many times as needed.
Almost all major programming languages feature one or more loop constructs.
``What's the point to talk about loops as a type of control flow outside of
the language context?'' you may be wondering.


A key building block for programming as loop is, it should have taken
developers' best effort to study the best practices.
It is unfortunate to see, however, that algorithmic implementations in production contain numerous
haphazard loops with floppy code before and after.
Many of them seem to just narrowly pass the `working' threshold
as if the developers were oblivious with the varieties of loop constructs or bother to
reduce the swollen initialization for their loop constructs.

This is so not because these developers have no appetite for better code.
A majority of them are not even aware that conscious choice of loop types and structures can make a
marked difference in the quality of code.


For this reason that I would like to devote this chapter to clear out the clouds over the
good practices of loops.
A large part of this chapter is on the topic ``How to tighten up slack loops?''
Another focus is on the question ``How to reduce nested loops to a single loop?''

Let us begin with an overview of loop constructs from several mainstream programming languages.
First off, one should ensure that control have a way to escape before entering a loop, otherwise
inadvertent infinite loop would result.
So all loop constructs are equipped with a conditional expression, a termination test.
The location of termination test is a distinguishing feature for a loop.
Based on its location, loop constructs can be classified as \emph{pre-test}, \emph{post-test},
and somewhere in between, \emph{mid-test}.
post-test loops attempt to execute the loop body at least once no matter what.
Mid-test loops may execute part of the loop body.


Many programming languages conveniently support more than one types of loop constructs.
\code{for}-loop and \code{while}-loop are examples of pre-test loop constructs that
almost all languages support.
\code{do-while}-loop is a post-test loop construct supported by \java, \cpp, C, and many
others (excluding \python).


~\autoref{tbl:loop-construct} summarizes the common parts in loop constructs of most high-level
programming languages.
On top of the standard loop constructs, possible customizations may be made with \code{break},
\code{continue}, \code{return}, \textit{etc.}, depending on the programming language of choice.
These statements blend into the loop body and fine tune the execution paths of otherwise standard
loops.

\section{Refactoring loops}\label{sec:refactoringLoops}

Many loops, embedded in a long functions, are there to search for a match and should be
refactored into a function of its own.
Doing so not only simplifies the original function, making the main logic stand out more, but
also the factored out function is compact, single-purposed, and readily reusable.

Another reason is the elimination of many intermediate, local variables.
Intermediate variables in a long function often share the same scope as the function
and thus contaminate the namespace for the rest of the code block.
Eliminating them will prevent many mysterious bugs and spare developers from such concerns.

The following example illustrates this.
In the first version, the code in the main function \code{execute} was
misappropriated---a large part of it was usurped for the search of a needle in a haystack in a loop.

After refactoring related code the loop into a separate function, we greatly reduced the bulge.
Most importantly, \code{target} and other intermediate variables, if any, may be eliminated and
will never pollute the namespace in the remaining part of the function.


\section{C-style For-loop}\label{sec:for-loop}

Beside the universal \code{while}-loop, another pre-test loop is the conventional
C-like \code{for}-loop
\footnote{This is not to be confused with the iterator-based foreach-loop such as
\lstinputlisting[basicstyle=\footnotesize]{loop/foreach-loop.java}
whose functionalities has been partly replaced by stream API as in \java.}
which looks like
\lstinputlisting{loop/for_loop.java}
The distinguishing parts of a \code{for}-loop are its header statements---the
initialization statement \code{<init>}, the loop continuation test
\code{<test>}, and the afterthought statement \code{<aftrth}.
Below is an explanation of each part:
\begin{enumerate}
    \item The \code{<init>} is a statement to be executed only once as control is transferred to
    the loop.
    \item The \code{<test>} may be regarded as the \emph{first} statement of the loop body.
    \item The \code{<test>} are executed one more time than the rest of loop body
    unless loop execution is aborted with, say, \code{break}.
    \item The \code{<aftrtht>} is the afterthought statement executed at the end of each
    iteration of loop body even in the presence of \code{continue}.
    But in the presence of \code{break} statement, \code{<aftrtht>} will be skipped together with
    part of the loop body.
    \item All three header statements are optional.
    Namely, `\code{for(;;);'} is perfectly legal and represents an infinite loop.
\end{enumerate}


Design considerations for a \code{for}-loop are summarized below.
\begin{itemize}
    \item
    What is the correct and minimal initialization?
    For example, should we initialize \code{int i = -1} or \code{int i = 0}?
    \item
    Where to update loop state?
    For example, where should \code{i++} or \code{j--} be placed?
    in the afterthought of the \code{for} header statement or somewhere in the loop body?
    \item
    What's the termination condition(s) how to arrange terminating statements if there are more
    than one of them?
\end{itemize}

The answers to these questions are interrelated and
shall be adjusted as a whole throughout the design and implementation of loops.
For example it is more flexible (sometimes necessary when certain condition
has to be met to increment/decrement)
to increment/decrement state variables in loop body but it is seldom the more concise form.
In a more concise loop, state updates are often done in the afterthought header statement.
For another, infinite loop is often the result of a reasoning loophole,
which causes incorrect termination condition.


The single biggest reason for me to use a \code{for}-loop is its limited scope of
loop variables.
Scope of loop variables declared in the \code{<init>} part of header statements are contained
within the loop.
For example the following code wouldn't compile
\begin{lstlisting}
    for (int i = 0; i < 10; ++i) {}
    System.out.println(i); // i is undefined
\end{lstlisting}
In contrast, loop variables used by the \code{while}-loop condition have to be declared
before the loop.
Therefore their scope last beyond the loop and this often cause problems for the subsequent
program for the aforementioned reasons.


Occasionally limited scope of \code{for}-loop may be a hinder for post-loop processing.
If that is the case, one may resort to
`one-more-loop' technique (see ~\autoref{subsec:one-more-loop} for more details) to solve the
problem.
Also for \python users, \code{for-else} or \code{while-else} is designed just for post-processing.


\section{The `\textit{loop-and-a-half}' problem}\label{sec:loop-and-a-half-Problem}

As discussed above, when it comes to programming with loops, there are a variety of constructs
such as pre-test loop and post-test loop.
Have you wondered why we need so many varieties and families?
Is there a one-size-fit-all loop?


To answer this question, let's dig into history a bit.
In 1966, Corrado B\"{o}hm and Giuseppe Jacopini proved that \code{goto} statements are
unnecessary and programs containing them can be transformed to use only conditional statements
and loops\cite{Bohm:1966}.
Along that line of thought, more researchers, who might have gone too far, attempted to remove
other `nuisance' in computer programming such as \code{break} and \code{return} in the middle of a
loop to reduce control flow complexity and promote code composability.
But the benefit cannot pay for the price.
For example, one result of doing so is that more local variables are needed.
Even worse, it exacerbates problems with duplicate code in and around a loop.
This is the origin of the so-called ``Loop and a half problem''\cite{Louden-Lambert-2011}.
Today, ``\textit{loop-and-a-half} problem'' is still a pestering problem for suboptimal loop
design and implementation.


At the language level, a number of loop constructs have been introduced to
minimize the symptoms of the ``\textit{loop-and-a-half} problem''.
But that's not enough.
It remains on developers to choose the most suitable loop constructs.
Further, code fine-tuning is beyond simple choices of loop constructs
and must be hand-crafted at implementation time.
In the section to follow, we will introduce `loop rotation', a technique for loop
optimization that helps alleviate `loop-and-a-half' symptoms.


\section{Loop Rotation}\label{sec:LoopDesignConsideration}
\begin{figure}[htb]
    \centering
    \includegraphics[width=.7\textwidth]{loop/ferris-wheel.jpg}
    \caption{\label{fig:loop-rotation}Loop as a circular sequence.
    The nodes \code{i++} and \code{print} are candidates that can matched and coalesced into
    the loop.}
\end{figure}


When implementing loops in programs, an important goal is to reduce duplicate code in and around
loop---be it pre-loop initialization or post-loop processing.
And one of the important techniques for that is `loop rotation'.


It is beneficial to visualize a loop construct as a Ferris wheel, a carousel, or a spool.
Mathematically speaking, a property is shared by all four---they are circular sequences, that is,
a sequence with rotational symmetry with respect to circular shifts.
If pictured as a Ferris wheel, distributed around the wheel are the conditional test,
initialization, state update statements and other statements in the loop body.
(see ~\autoref{fig:loop-rotation}).


\begin{figure}[htb]
    \centering
    \begin{subfigure}{.45\textwidth}
        \includegraphics[width=\textwidth]{loop/loose-spool.jpg}
        \caption{\label{fig:loose-spool} Sloppy, duplicate code is analogous to loose, unorganized
        thread near a spool.}
    \end{subfigure}
    \begin{subfigure}{.45\textwidth}
        \includegraphics[width=\textwidth]{loop/tight-spool.jpg}
        \caption{\label{fig:tight-spool} Coding technique, \textit{e.g.}, `loop rotation', can help
        reduce duplicate code and is pictorially depicted as winding up threads neatly onto a
        spool.}
    \end{subfigure}
    \caption{\label{fig:spool-loop}Craftsmanship in loop programming is analogous to organizing
    threads using a spool.}
\end{figure}


As if a ring may be cut open, the nodes in a circular sequence may be ordered as a linear sequence
if counting counterclockwise starting with the lowest node.
In doing so, every statement may be the `first' (or `last') depending on which
node is positioned lowest.
One thus may take advantage of this rotational degrees of freedom to
fine tune loop implementation by `rotating' the loop to match up and coalesce duplicate code in the
affinity of the loop.
This process is referred to as `Loop rotation'.


Another helpful picture is to think of loops as spools and programs as threads with loops
introduced to help organize threads.
Redundant code outside of the loop may coalesce into the loop body during a `loop rotation'
like winding up loose thread onto a spool (~\autoref{fig:spool-loop}).


In practice, one may first implement a non-discriminating loop,
such as \code{while (true)} or \code{for (; ;)}, for prototyping purposes.
This will push all the statements into the loop body for ease of `loop rotation'.
One can focus on coding up a working solution first.
Once a working solution has been found, one often has gotten a good grasp of the ins and outs of the
implementation.
%to to try to spool up slack threads as much as possible by `rotating the loop' to match and
%eliminate duplicate code.
Then one can start `rotating the loop'---rotating the statements in the loop body, match up and
eliminate `unwound', duplicate code before or after the loop.
In the end, one can try different loop constructs, move and fit state-updating statements,
combine or annihilate \code{continue} and \code{break} statements, \textit{etc.}
If needed, repeat the above steps until the code is acceptable both functionally and
aesthetically.


As you can see, a large part of the hard work for programming a loop lies outside of the loop.

\section{Loop Initialization}\label{sec:loopInitialization}

In light of the `loop rotation' technique, let us now go into details about
loop initialization.
Initialization is a preclude, a bridge to the main loop body.
It is a `primer coating' that makes a substrate for the loop to work on.

The single most important requirement for loop initialization, apart from being `correct', is
`small'.
Each has its focus---let a minimal, light-weight initialization do the preparatory work
and the rest of the loop do the weight-lifting work.

Simple?
Simple.
This may sounds hard but actually simple.
But to achieve this goal it is required that one form a habit of striving for the simplest
initialization when facing similar situations.

Let us take a look at the 'spiral termination' problem:
\begin{quote}
    Given the dimensions, $m, n$, of a matrix,
    suppose one is to visit each and every cell of the matrix in
    a clock-wise spiral fashion starting from $[0,0]$.
    Determine where the process terminates.
    For example, when $m=1,n=1$, it terminates at $[0,0]$
\end{quote}

There are more than one solutions to this problems---iterative and recursive.
But apparently we are here to demonstrate an iterative solution with a loop.
Note that the problem only asks for the terminating position and
cells passed by along the way are irrelevant.
Skipping the rationale, I am going to state the algorithm to be implemented:
\begin{quote}
    We are going to `stride' toward the terminating position.
    In each stride, we leap passing one `layer' of cells.
    A `layer' here consists of all the cells not yet visited but not completely surrounded by
    unvisited neighbors.
\end{quote}
\begin{figure}[tbh]
    \centering
    \includegraphics[width=.4\textwidth]{loop/spiral-term.jpg}
    \caption{\label{fig:spiral-term-iter}
    Iteration after one `spiral stride' in the `Spiral termination' problem.}
\end{figure}
In a big enough matrix, if we start off at $[i,j]$, then after we finish going
around and visiting all the cells in one `layer', we would end up at $[i+1,j+1]$
as shown in ~\autoref{fig:spiral-term-iter}.
Please note that there is a special case---when the matrix is an array
(either columnar or row) or, after being peeled off, becomes one,
what remains are cells forming a straight line.
In that case, the terminating cell is at end of the line.
For now, we are going to handle this extra complication with post-loop processing.

At the first glance, initializing $i=0,j=0$ seems straightforward and reasonable.
For example, when $m=3,n=3$, after `peeling off' the outer layer, \code{i,j} becomes
$[1,1]$ and indeed the process terminates on $[1,1]$.
However we will encounter problem for case $m=2,n=2$, for after the outer layer, there is nothing

\section{Minimal Post-loop Processing}\label{subsec:one-more-loop}

Conversely, the `loop rotation' technique may be applied to reduce redundant post-loop processing.

If you find that after the loop, your code is doing similar things as a loop iteration does, then
you should probably consider using the `One-more-cycle' coding technique that I am explaining next.

Sometimes after loop is completed, non-trivial post-processing is needed to transform the output

\section{Loop Pacing}\label{sec:linearVs.NonlinearStepping}

Loop pacing is another aspect of a loop that has been largely ignored especially when tuning loop
construct.
Usually it is changed when the state-updating statements are changed, for example, when moved
between the afterthought position and the loop body.


Deterministic linear stepping \textit{vs.} nonlinear or conditional stepping.

If viewed as a state machine automaton, loop variables, serving as state registers, may change
linearly as loop is executed, or not.
In some cases, one can simply step through linearly, one element at a time.
In others, one need to step through with a varying pace conditioned by the elements encountered,
and this is called `nonlinear stepping' in the following context.
Nonlinear stepping has important applications in implementation of complex algorithms.
\code{while}-loop is more accommodating for all kinds of stepping.
For \code{for}-loop, if you see the afterthought part missing, that's probably a sign for
nonlinear stepping.
If you use \code{for}-loop for linear stepping,
please try your best to afterthought part for increment or decrement purposes.

    A = [2,3,1,1,4], return true.

\end{quote}

\section{Conclusion}

The best practice when it comes to programming with loops, as any other types of coding,
is to get a \emph{working version} (WV).
Once you get a WV, you can spot for areas of improvement:
duplicate code of any severity, excessive customization such as \code{break} or \code{continue}
\textit{etc}.
Try the techniques we talked about in this chapter such as `loop rotation',
`one-more-loop', initialization reduction techniques, \textit{etc.}
Try on different loop constructs and so on.
Also keep in mind opportunities of using sentinels for certain niched applications (see
~\autoref{ch:sentinels}).
Finally, narrow down to a loop construct
that is a close match to your programming requirement
minimal loop customization, if needed at all.
The ultimate goal is to minimize or eliminate duplicate code in and around loop.
