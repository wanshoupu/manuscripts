\chapter{Tighten Up the Loops} \label{ch:loops}

All major programming languages feature one or more loop types as control flow and
it is one of the most widely used building block.
Loop is a programing productivity amplifier---with a static loop body and
a scarce of overhead code (\textit{e.g.}, loop variables), the loop may be executed as many
times as needed.
But many developers often haphazardly stumble upon a first-working loop and settle.
Seldom anyone would try to think about the difference between the varieties of loops,
even fewer people would try different loop structures and loop types and see
which best fits the current situation.
This is so not because these developers have no appetite for better code.
A majority of them are not even aware that conscious choice of loop types and structures can make a
marked difference in the quality of code.
Therefore, I dedicate this chapter as a primer to the topic ``How to close your loop?''
and I meant it literally.

``Why!'' you say, ``What's the point for you to talk about loops as a type of control flow
outside of the language context?''
Yes, there are so much to say about loops in their generic sense.
Similar to the structure in ~\fullref{ch:organizeYourIfElse}, I will share mostly my first-hand
coding experience throughout the presentation of the chapter.
Beyond that, this chapter is also presented for completeness since
later discussions of the interactions between conditional statements and loop is built on
top of reader's mastery of loop programming.
But most importantly, I intend this chapter to serve as an inspiration to other enterprising
programmers to reflect on why they code the way they do and find out ways to improve.

            Component & Description \\
            \hline
            \emph{Loop initialization} &
            This is the preparation section before the execution of a loop.

            The condition for control to enter (or continue) the loop. \\
            \emph{Loop body} &

This section is an overview of loop constructs in mainstream programming languages.
Before entering a loop, control must have a way to escape.
So practically all loop constructs are equipped with a test statement for that purpose.
The location of test statements is a distinguishing feature for a loop.
Based on the location of the test statement, loop constructs can be
classified as \emph{pre-test} and \emph{post-test}.
\code{for}-loop and \code{while}-loop are examples of pre-test loop constructs that
almost all languages support.

\code{do-while}-loop is a post-test loop construct supported by \java, \cpp, C, and many
others (except \python).
\code{do-while} loop attempts to execute the loop body at least once no matter what.

For convenience, programming languages support one or more types of loop constructs.
\@\autoref{tbl:loop-construct} describes the components of common loop constructs
in high-level languages.
On top of the standard loop constructs, customizations are made possible with \code{break},
\code{continue} or \code{return}, depending on the programming language of choice.
These statements blend with the loop body and provide alternative execution paths to a standard
loop construct offers.

\section{A word on the usage of \code{continue}, \code{break}, and \code{return}}
\label{sec:continue-and-break}

Bare use of \code{continue} and \code{break} in a loop is very rare (maybe only for educational
reasons).
Use of \code{continue} and \code{break} in a loop is usually done within a \code{if}-branch.

For most of the simple cases, the functionality realized by using \code{continue} statement can be
equivalently produced by adding an \code{else}-clause.

\section{C-style For-loop}\label{sec:for-loop}

Beside the universal \code{while}-loop, another pre-test loop is the conventional
C-like \code{for}-loop as \lstinputlisting{loop/for_loop.java}
This is not to be confused with the iterator-based \code{for}-loop such as
\begin{lstlisting}
    for (Object obj : list)
\end{lstlisting}
which has been largely made obsolete with stream-like coding styles in \java.

There are some interesting aspects about \code{for}-loop header statements.
\begin{enumerate}
    \item The \code{<init>} is a statement to be executed only once as control is transferred to
    the loop.
    \item The \code{<test>} may be regarded as the \emph{first} statement of the loop body.
    \item The \code{<test>} are executed one more time than the rest of loop body
    unless loop is terminated with a \code{break} statement.
    \item The \code{<aftrtht>} is the afterthought statement executed at the end of each
    round, unless loop terminates with a \code{break} statement.
    \item The \code{<aftrtht>} is always executed as many times as the rest of loop body
    even in the presence of \code{continue}.
    \item All three header statements are optional.
    Namely, you may legally code `\code{for(;;);'} for infinite loop.
\end{enumerate}


Design considerations for a \code{for}-loop are summarized below.
\begin{itemize}
    \item
    Preparation code for a loop is called initialization
    and it determines the starting point of the loop.
    What's the best initialization?
    Should it be \code{int i = -1} or \code{int i = 0}?
    \item
    When and where should state updates?
    For example, where should \code{i++} or \code{j--} be placed?
    in the 3rd part of the \code{for} statement?
    or in the body?
    It's more flexible (sometimes necessary when certain condition
    has to be met to increment/decrement)
    if the increment/decrement is in the body.
    But it's more concise if done in the afterthought of a for-statement.
    \item
    What's the termination condition and How many termination points?
    Many a time, infinite loop is resulted when incorrect assumption is made
    about the termination condition.
\end{itemize}

One desirable feature of a \code{for}-loop is the limited scope of its loop-variables---
scope of loop-variables are contained within the loop.
For example the following code wouldn't compile
\begin{lstlisting}
    for (int i = 0; i < 10; ++i) {}
    System.out.println(i); // i is undefined
\end{lstlisting}
In contrast, loop variables used by the \code{while}-loop condition have to be declared
outside of the loop and extends beyond thereafter.
Sometimes this causes inadvertent namespace pollution that leads to treacherous bugs.

Occasionally limited scope may be a hinder for post-processing with \code{for}-loop.
I will often balance out the trade-offs and if I choose \code{for}-loop, I will use
`one-more-loop' technique (see ~\autoref{subsec:one-more-loop} for more details) to beat
post-processing outside of the loop.
For \python users, \code{else}-clause for post-processing.

In practice, I often
start with \code{while (true)} or \code{for (; ;)} for prototyping and as a reminder to
myself that this piece of code is temporary.
Once that is working, I often have gotten a good grasp of the problem and the solutions.
Then I will start crafting the loop by trying different loop constructs, moving and fitting
variable increment statements,
combining or annihilating \code{break} or \code{continue} statements \textit{etc.}

\section{The `\textit{loop-and-a-half}' problem}\label{sec:loop-and-a-half-Problem}

As discussed above, there are a variety of loop constructs and loop families such as
pre-test loop and post-test loop.
Have you wondered why we need so many varieties and families?
``Is there a one-size-fit-all loop?'' you ask.
To answer this question, we need to start with a research dated back 1966.
In 1966, Corrado B\"{o}hm and Giuseppe Jacopini proved that \code{goto} statements are
unnecessary and programs containing them can be transformed to use only conditional statements
and loops\cite{Bohm:1966}.
Along that line of thought, more researchers, who might have gone too far, attempted to remove
other `nuances' in computer programming such as \code{break} and \code{return} in the middle of a
loop to reduce control flow complexity and promote code composability.
But the price of doing so may not pay the benefit it brings.
More local variables are needed.
Even worse, it may require duplicate code before or after a loop.
This is the so-called ``Loop and a half problem''\cite{Louden-Lambert-2011}.

So in disguise, the \textit{loop-and-a-half} problem is code duplication problem
caused by unnecessarily restricting immature termination within a loop.
Variety of loop types are introduced to minimize the symptoms of the \textit{loop-and-a-half}
problem.

What is the simple boundary conditions to be used for initialization?
It may not be so straightforward because it really depends on the specific problem.
But more often than not, the initialization part of a loop is simple, effortless,
intuitive values---integer $0$, empty list, zero-length string, array of simple values,
\textit{etc}.
As an example, ~\autoref{lst:fibonacci} illustrates the initialization of the Fibonacci sequence
with its first two elements: $0$ and $1$.
\lstinputlisting[label={lst:fibonacci},
caption={A cached solution for the $n$th Fibonacci numbers.}]
{loop/fibonacci.py}
Note that we have `back-filled' the Fibonacci numbers to the $0$th element as $0$.
You will see more cases later where some generalization of the algorithm and/or the mathematical
concept behind will make the coding much easier.
This effort of simplifying initialization process is especially important for dynamic programming
where often the boundary conditions are
usually an array of simple values.
See ~\autoref{ch:dp} for more information.
If you find that your initialization code actually repeats the loop body in whole or in part,
or that the post-processing logic does similar things that
the loop does,
That's a sign to `tighten' your loop, to absorb the pre-loop and post-loop logic
into the loop.
what can you do to get rid of them?
In the next couple of sections, we are going to present tips that can help you alleviate
symptoms associated with `loop-and-a-half' problem.

\section{Loop Rotation}\label{sec:LoopDesignConsideration}

It is beneficial to visualize a loop construct as a roulette, a carousel, or a Ferris wheel, all
three of which shares the properties of a circular sequence---an sequence with rotational
degree of freedom.
Even after everything has been laid out onboard, there are still rotations as degrees of
freedom as shown in ~\autoref{fig:loop-rotation}.
Thus, one of the task in
loop design is to arrange loop logic in circular sequence and pick the best
entrance and termination ports.

\section{`One-more-cycle' coding technique}\label{subsec:one-more-loop}

Sometimes after loop is completed, non-trivial post-processing is needed to transform the output
to final answer and that happy to share part of the logic of the loop body.
To reduce duplication of code, one can use the `one-more-cycle' technique---
instead of
\begin{lstlisting}
    for (int i = 0; i < list.size(); ++i)
\end{lstlisting}
and then repeat part of the loop body in post-loop processing logic,
do
\begin{lstlisting}
    for (int i = 0; i < 1 + list.size(); ++i)
\end{lstlisting}
and with an \code{if}-branching, hitchhiking part of the loop body to do the processing
for the last iteration and return the final result.
\@\autoref{lst:largest-rectangle-histogram} is an example of such usage for solving the
`largest rectangle in histogram' problem

\section{Linear stepping \textit{vs.} nonlinear stepping}\label{sec:linearVs.NonlinearStepping}

If viewed as a state machine automaton, loop variables, serving as state registers, may change
linearly as loop is executed, or not.
In some cases, one can simply step through linearly, one element at a time.
In others, one need to step through with a varying pace conditioned by the elements encountered,
and this is called `nonlinear stepping' in the following context.
Nonlinear stepping has important applications in implementation of complex algorithms.
\code{while}-loop is more accommodating for all kinds of stepping.
For \code{for}-loop, if you see the afterthought part missing, that's probably a sign for
nonlinear stepping.
If you use \code{for}-loop for linear stepping,
please try your best to afterthought part for increment or decrement purposes.

\section{Conclusion}

The best practice when it comes to programming with loops, as any other types of coding,
is to get a \emph{working version} (WV).
Once you get a WV, you can spot for areas of improvement:
duplicate code of any severity, excessive customization such as \code{break} or \code{continue}
\textit{etc}.
Try the techniques we talked about in this chapter such as loop rotation, include
`one-more-loop',
try on different loop constructs and so on.
Also keep in mind opportunities of using sentinels for certain niched applications (see
~\autoref{ch:sentinels}).
Finally, narrow down to a loop construct
that is a close match to your programming requirement
minimal loop customization, if needed at all.
The ultimate goal is to minimize or eliminate duplicate code in and around loop.
