\chapter{Organize your \ilcode{if-else} statements}\label{ch:organizeYourIfElse}

\code{if-else} is a flow control that branches control depending on a condition.
Many books and articles already give \code{if-else} flow control comprehensive discussions,
\textit{e.g.},
Wikipedia\footnote{\url{https://en.wikipedia.org/wiki/Conditional_(computer_programming)}}.

It may be strange that I am actually spending a full chapter on this.
Believe me that this is so basic and so important only willful endeavor can bring an experienced
developer to the beautiful, succinct solution.

Based on my interaction with many developers at top-tier tech companies,
every minute spent on studying the basics like \code{if-else} is worth the time before we do code
reviews on their pull requests in production code.

When I see twisted logic in code that attempts to branch between $A$, $B$, and $C$, I see through
it a fierce battle that the author has undergone to get the logic working.

The author has my sympathy for his or her unprepared struggle.

In this chapter, I'm going to share my experience of how to balance out \code{if elseif
else} switching statements to reduce redundancy condition checks on the one hand and duplicate
code on the other.

The techniques I employ is of math origin.
I'm going to review basic Boolean algebra such as logical equivalences, normal
forms, \textit{etc.}, and demonstrate how to apply these in logic simplification.

In doing so, I hope programmers would be inspired how to fight the battle of logic simplification.

\section{\code{if-else}-condition}\label{sec:if-else-condition}

A boolean variable has two values-\code{true} and \code{false}.
A simple condition in a \code{if-else} test has two branches-that in the \code{if}-block or that
of the \code{else}-block;
A composite condition of two boolean variables connected by logic operators \code{or} and
\code{and} will has 4 branches;
and so on.
But when disguised in real problems, especially when some combinations are omitted, logic
simplification will not be so straightforward.

\section{Build up your case step-by-step}

The correct way to design the implementation of recursive, case-based testing code implementation is to do testing / checking such that knowledge is built up piece-by-piece.
To inspect for logic holes and false assumptions, do it backward: from the very end go to the start, find out if the knowledge needed to perform the current line of code is in place. Any missing knowledge will result in exception.
