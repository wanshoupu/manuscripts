\chapter{Organize your Conditional Statements}\label{ch:organizeYourIfElse}

Conditional is a control switching mechanism to alter code execution path,
conditioned by boolean expressions.
As a control flow, conditional is one of the fundamental building blocks
of almost all programming languages.
Undoubtedly, many references---textbooks, research articles, blog posts---have already covered this
comprehensive discussions
\footnote{\url{https://en.wikipedia.org/wiki/Conditional_(computer_programming)}}.
It may seem strange that I am spending a chapter on such a `well-known' topic here and now.
However, just because the topic is basic and `well-known' does not mean that many folks can do it
right or will do it right.
But based on my years of working experience in several top-tier tech companies, it is often
the haphazard first working version that makes its way to production codebase and becomes the
core for millions of businesses, it does not matter how crooked the design may be, how
obscure the logic may be.
%But it is seldom the case that the first version of implementation of any non-trivial logic, if
%correct at all, is optimal.
%It fails the primary purpose of communication with other humans.
%Worse, it often results in redundant/duplicate code.
``As long as it works, why should one bother to simplify the logic?'', you may argue.
As a response, I'd like to quote Steve McConnell:
``..the primary audience [of your code] is made up of humans, not computers.''\cite{Mcconnell.2004}.
\begin{quote}
    ``Any fool can write code that a computer can understand.
    Good programmers write code that humans can understand.''\\
    —Martin Fowler
\end{quote}

Twisted code and intertwined logic are often unsimplified
products out of fierce battle fought by a struggling developer.
Though hard to read, understand, debug, and modify, they should not be regarded as enemy.
On the opposite, they are the dawn of simple, effective implementation
and the rest of this chapter is dedicated to show you how.
%Communicate clear, succinct code to colleagues and successors are much more efficient.
I'm going to share my experience of how to polish complicated logic involving conditionals into
simple, beautiful, and succinct code.
You will learn how to organize branching statements using clauses such as \code{if}, \code{else if}
(or\code{elif}), \code{else}, \textit{etc.},
\code{if elseif else} to produce effective, succinct logic.
You would minimize occurrences of redundancy condition checks in your code and reduce
duplicate code overall.
Every minute you spend on grasping the basic conditional programming is worthwhile before
plunging into other topics.
Through plenty of examples, I demonstrate how to apply these techniques for logic simplification.
In doing so, I hope programmers would be inspired to the beautiful, succinct conditional statements.

\section{Basic techniques for conditional statement simplification}
\label{sec:conditional-simplify-tech}

Some of the techniques I employ in this section is of math origin, especially basic Boolean algebra
such as logical equivalences:
double negation elimination, De Morgan's laws, distributive law, \textit{etc.}
and normal forms: disjunctive normal form (DNF) or conjunctive normal form (CNF).
Review and refresh your memory on relevant materials as you see fit.

A boolean variable or expression can evaluate to two possible values-\code{true} and \code{false}.
Depending on the evaluation result of a boolean value,
a \code{if-else} test has two execution alternatives-the \code{if}-block or
the \code{else}-block;
A composite condition consisting of two boolean values may have up to 4 alternatives.
Three boolean values make have up to 8 alternatives.
And so on.

            code & condition to execute \\
            \hline

Nevertheless, this is a good starting point for further improvement.
What's important is to keep on working---do not settle on half-cooked solution.

So upon arriving at this first solution, I decided as a next step to eliminate the nested
conditional statements.
Observed that the \code{else} block of \code{if (test1)} is much simpler, I decided to flip
the logic by negating \code{test1}.
Then I promoted the nested \code{if (test2)} up to the first-level so that overall they
become sequential conditional statements comprised of \code{if\{..\}else if\{..\}else\{\}} blocks
that are built on top of one another.
This turns out to be a coding pattern that I'm going to spend more time to explain
in ~\autoref{sec:case-stack}.
The resulting code is as shown in ~\autoref{lst:simpleBranching}.

Now the conditional statements are streamlined, straightforward and are easily understood at a
glance.
Comparing with ~\autoref{lst:nestedBranching}, it is a big improvement.
But still it has duplication code (both \code{statement2} and \code{statement3} are repeated).
So I did a back-of-envelop calculation on a napkin---for each of the three statements
(which consists of the conditional block body),
I wrote down the conditions for the corresponding block to be executed.
The result is shown in ~\autoref{tbl:breakdown-of-conditions}.
With this table, it is clear that the key to simplify the logic lies in the conditions for the
execution of \code{statement2}.
Let us do some Boolean algebra.
Let $c$ be the condition for \code{statement2} to be executed and
\begin{align*}
    a &= \text{\code{test1}}, \\
    b &= \text{\code{test2}}.
\end{align*}
Then
\begin{align}
    c &= a \land \lnot b \lor \lnot a  \nonumber \\
    &= a \land \lnot b \lor (\lnot a \land \lnot b \lor \lnot a \nonumber) & \text{// absorption law
    }\\
    &= (a \land \lnot b \lor \lnot a \land \lnot b) \lor \lnot a \nonumber & \text{// associativity
    law}\\
    &= \lnot b \lor \lnot a & \text{// distributivity law} \nonumber \\
    &=\lnot (a \land b) & \text{// De Morgan's law} \label{eq:boolean-expression-simplify}
\end{align}

~\autoref{eq:boolean-expression-simplify} shows that the condition of execution for
\code{statement2} is \code{!(test1 && test2)} and this can be made as the \code{else}-clause of
of the conditional construct for \code{statement1}, which is \code{if (test1 && test2)}.
With this hard-earned wit, it now becomes straightforward to come up with yet an even simpler
implementation such as ~\autoref{lst:final-simplified-conditional-statement}.

Please note that the above process is not the only way to arrive at simplified logic.
Another possible way to achieve same logic simplicity is to use `truth table'.
Let's see how this works.
\begin{table}[h]
    \begin{center}
        \caption{True value table for \code{test1} and \code{test2}.
        \label{tbl:true-value-table}}
        \begin{tabular}{|c|c|c|}
            \hline
            \code{test1} & \code{test2} & true expr \& execution\\
            \hline
            \code{false} & \code{false} & \code{!test1} $\rightarrow$ \code{statement2} \\
            \code{false} & \code{true} & \code{!test1} $\rightarrow$ \code{statement2} \\
            \code{true} & \code{false} & \code{test1 \&\& !test2}
            $\rightarrow$ \code{statement2} \\
            & & \code{test1=true} $\rightarrow$ \code{statement3} \\
            \code{true} & \code{true} & \code{test1 \&\& test2} $\rightarrow$
            \code{statement1} \\
            & & \code{test1} $\rightarrow$ \code{statement3} \\
            \hline
        \end{tabular}
    \end{center}
\end{table}
I have constructed truth table as ~\autoref{tbl:true-value-table}.
Since there are two conditional variables \code{test1} and \code{test2}, there are
total four entries in the truth table.
The third column shows the boolean expression that's evaluated to \code{true} by which
the execution of the statement ensues.
Summarizing the table entries, we arrive at the following conclusions
\begin{enumerate}[label={\roman*:}]
    \item \code{statement1} is executed iff both \code{true};
    \item \code{statement2} is executed iff not both \code{true};
    \item \code{statement3} is executed iff \code{test1=true}, regardless of
    \code{test2}.
\end{enumerate}

With all the mental twists untied, implementation of something like
~\autoref{lst:final-simplified-conditional-statement} naturally follows.

We conclude this section with the presentation of two methods for logic simplification.
In practice, you may find one or the other process to be more effective under certain circumstances.
You are encouraged to try out both ways and for your own instinct about the methods.

\section{Build up your cases in \code{if}-stack}\label{sec:case-stack}

One frequently faces need of multi-way switching.
One can realize this with nested \code{if..else} statements like ~\autoref{lst:nested_if_else}.
\lstinputlisting[label={lst:nested_if_else}]{if-else/nested_if_else.java}
The nesting level will go deeper with more switching fanouts and
the logic becomes unwieldy pretty quickly.
As an alternative with better readability, one can organize multi-way switching with an
\code{if}-stack.
A \code{if}-stack refers to a stack of \code{if}, \code{else if} (\code{elif} for \python), or
\code{else}.
For example the ~\autoref{lst:nested_if_else} complexity can be equivalently written as
\lstinputlisting[label={lst:if-stack}]{if-else/if_else.java}
Sometimes a \code{switch}-statement may be equivalently used in place of a \code{if}-stack on
limited use cases.
But we are going to limit our discussion to \code{if}-statement for now.

The execution of an \code{if}-stack is like walking up a staircase---one
builds up cases by successive tests in a step-by-step fashion.
The conditional expression of the leading \code{if}-clause is the first step of check.
If it is evaluated to \code{true}, then the \code{if}-clause is executed
and the rest of the stack is skipped.
Otherwise, the conditional expression of the next branching clause is evaluated
and so on until the end of the \code{if}-stack.
Note that \code{if}-stack may not be in the form of \code{if..else if..else}.
With the presence of \code{return} and \code{break}, a series of \code{if}-statements can also
form an \code{if}-stack.

When taken apart, the conditional expressions of \code{if}-stack
are cumulative---a later case combines all earlier conditionals with its own.
For example the ~\autoref{lst:if-stack}, if taken apart, will be
\lstinputlisting[label={lst:if-stack-taken-apart}]{if-else/if_else_taken_apart.java}
Note that the three \code{if}-blocks are totally independent and
the order among them does not matter any more.
Apart from this ordering flexibility, the code readability and
the performance of ~\autoref{lst:if-stack-taken-apart} is
generally speaking worse than ~\autoref{lst:if-stack} as it does a significant amount of
redundant tests.
When inspecting code for logic fallacies and unfounded assumptions, for example, one has to keep
this cumulative effect in mind: all the assumptions about the
the current line of code should have been tested by exactly one of the conditionals ahead.
A missing test will likely result in exception.
From this perspective, the alternative form ~\autoref{lst:if-stack-taken-apart} may be more
straightforward to spot untested assumptions made for a later case than its \code{if}-stack
counterpart.

\begin{figure}[htb]
    \lstinputlisting[label={lst:if-stack-equals},
    caption={Example implementation overriding \code{equals} in a subclass}]
    {if-else/equals.java}
\end{figure}
As an example of \code{if}-stack, let's consider the implementation of method
\code{equals(Object obj)} as shown in ~\autoref{lst:if-stack-equals}.
The first test we do is the nullity of the argument.
If it is not null, then we test if its of type \code{MyClass}.
Only if it is not null and is of type \code{MyClass}, we cast it to type \code{MyClass}
and test equality between member variables of
\code{this} instance and \code{that} instance, pairwise.
From this example, you see how we build up the cases like a staircase step-by-step cumulatively.
As another example, let us consider the code for determining the lowest common ancestor
of two values in a binary search tree.
This is a typical problem where the cases to be tested can be combinatorial
if not handled properly, your code can blow out like crazy.
But if we design our \code{if}-stack properly, a couple of lines of code can handle all the
combinations like a breeze.
Take a look at ~\autoref{lst:if-stack-lca}.
The cases are built from ground up:
\begin{enumerate}
    \item Test nullity;
    \item Test for left branching;
    \item Test for right branching;
    \item Test for existence of keys;
    \item Final case;
\end{enumerate}
Note later statements are built on the assertions of previous tests---test for left/right
branching requires the non-null attributes of root otherwise the code will throw
\code{NullPointerException}.
Also note that as the cases are being built up, the solution spaces are also being ruled
out---each time we eliminate a half-space with a test---much like that of a binary search.
\begin{figure}[htb]
    \lstinputlisting[label={lst:if-stack-lca},
    caption={An implementation of finding lowest common ancestor in a binary search tree.}]
    {if-else/lca.java}
\end{figure}
Some source states that when designing \code{if}-stack do the simple tests first.
I think that's a superfluous observation.
The underlying rule is to do the most informative test first.
That way, the solution space would be squashed at the earliest possible time.
Building up the cases of an \code{if}-stack is ultimately empirical.
Even the experienced developers may have to make a couple of attempts to get it right.

The questions when it comes to thinking of the base cases are:
What if the matrix is a row array?
Column array?
What if the matrix is a one-cell matrix?
Extreme question: what if the matrix is empty?
Do you just throw exception?
