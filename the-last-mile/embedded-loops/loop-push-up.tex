\chapter{Nested Loop Compression} \label{ch:loop-thinning}

We have laid the foundation about loop programming in ~\autoref{ch:loops}.
In this chapter, we are going to address another common misbelief about nested loops.
It is one of the common mistakes that an inexperienced developer tends to make is using
nested loop where a seasoned developer would have avoided.
Although permitted by most programming languages, nested loops almost always bring about
hindrance to code readability.
%More often than not, they are mere nuisances when one tries to understand the semantics
%or analyze the runtime complexity.
Occasionally, inadvertent usage of nested loops even becomes the cause of degenerate runtime for
suboptimal implementations---namely, what could have been $O(N)$ becomes $O(N^2)$.


The difficulty of adopting a new programming habit in this regard is
awareness---when compelled to use a nested loop, developers need to take a step back
and think over the options.
When it comes to algorithmic implementation using nested loops, the rule of thumb is ``Be cautious'.
More often than not, nested loops are not necessary and can be compressed into single-layer,
dynamically paced loops with the help of auxiliary data structures, cascade conditionals, and so on.


The only scenario where nested loops find sound usage for is iterating through $2$D or
higher
dimensional data structures like list of lists, matrices, \textit{etc.}
With a tuple of indexes, \textit{e.g.} \code{i, j}, nested loops seem like a must.
Even in such cases, the readability of the code is still a problem and confusion often raises
about which index is for which dimension.
Therefore opportunities still exist for one to refactor nested loops.
For example, more meaningful
functions with meaningful names for better code readability and reusability,
each containing a single loop.
Some may argue that function invocation overhead may hurt performance especially inside a loop.
My answer to that is that if you really care about performance you would have vectorized
your code to use built-in matrix operations instead of nested loops.
%But whichever way you go, it involves function calls.


\section{Empirical Loop-thinning Technique}\label{sec:loop-thinning-technique}


%First working version is seldom the best solution.
%Let us ask this question: ``Under what circumstances can nested loops be replaced by thinner
%loops?''
Many situations that nested loops appear so compelling or even inevitable are not so
in retrospection.
We are going to present techniques that help guide one to coalesce nested loops
into a single loop in certain scenarios, which we
generally refer as `loop thinning' technique.
One particular case that almost comes with guaranteed success is nested loop where
the outer loop represents an evenly-paced, end-to-end iteration whereas on the inner loop is
performed a partial lookup either on an auxiliary data structure or
from a `sliced view' on the same data structure.
%(for example, an array slice from the starting point to the current index).
%When an auxiliary data structure is used, it is used to provide cumulative, partial
%information in addition to the main data structure.


As result of the `loop thinning' process, one or more of the following may
be true:
\begin{itemize}
    \item Use of extra conditional construct or test;
    \item Pacing of outer loop becomes more dynamic;
    \item Extra boundary condition handling logic;
    \item Use of additional auxiliary data structures for the outer loop, such as a queue or stack.
\end{itemize}


\begin{figure}
    \centering
    \includegraphics[width=0.6\textwidth]{embedded-loops/segment-for-loop-thinning.jpg}
    \caption{\label{fig:segment-for-loop-thinning} Sectioning of loop body statements
    for `loop thinning' process.
    Each section receives different treatment during the `loop thinning' process.}
\end{figure}
Depending on the relative position with respect to the inner loop, the body of the outer loop is
divided into three sections---for sake of argument, we will call them
pre-inner-loop section, inner-loop section, and post-inner-loop section
(shown in ~\autoref{fig:segment-for-loop-thinning}).


The gist for flattening nested loops is as follows.
First, use `loop rotation' technique (see ~\fullref{ch:loops})
to move pre-loop statements out of the way;
%Then internalizing the condition of inner loop so that it becomes an unconditional loop, if not
%already---for example,
%by converting the loop condition as a conditional \code{break} statement inside the loop body;
The second step depends on the inner loop construct.
If the inner loop has a non-trivial loop condition, then the inner loop can
be converted to a conditional construct as-is by keyword swapping---\code{while} $\rightarrow$
\code{if}.
At the same time, the post-inner-loop statements shall be wrapped away in an \code{else}-clause
piggybacking the newly formed conditional.
On the other hand, if it is an unconditional loop, chances are that a conditional \code{break}
statement is somewhere in the loop body.
Then one can tuck the post-inner-loop statements under the conditional of the
\code{break} statement.
Then the inner loop can be stripped away along with the deletion of the \code{break} statement.


%shield post-loop statements in a conditional clause, probably in the `\code{else}-block' of the
%to-be-formed conditionals of next step;
%shield the post-loop statements in an additional conditional block.
%convert the inner loop---if it is an unconditional, infinite loop, just remove it, if with a
%condition, convert it to a conditional or prepend to an existing one
Finally, with the newly formed conditional statements,
one may refer to the best practices presented in ~\autoref{ch:conditional-cascade}
to optimize the loop body into cascade conditionals.
Throughout the process, please pay special attention to bypassing statements, such as
\code{break} and \code{continue}.
%Note that the order of the last two steps, creating the conditional and creating the
%\code{else}-clause, may be adjusted depending on the situation---it is essentially a
%`chicken or the egg' problem.


Additionally here are some preparatory tips for those who are new to this.
Where needed before one starts, one shall take apart compound statements, especially the
non-idempotent conditions.
Compound statements may get in your way of refactoring for multiple reasons.
The most prominent one is that the components of a compound statement
may be broken down and put at different places for `loop thinning' refactoring.
Non-idempotent expressions in the condition of conditional statements are even more troublesome
because their the mere test of the condition may irreversibly alter the state of the loop.
For example,
\begin{lstlisting}
    while (++i < LIMIT);
\end{lstlisting}
shall be expanded to
\lstinputlisting[]{embedded-loops/expanded-do-while.java}
before the start of loop thinning refactor.
The following Golang statement should also be unfolded beforehand:
\begin{lstlisting}
    if v := a[i]; v < LIMIT
\end{lstlisting}


For similar reasons, \code{for}-loop with all its header statements, should be taken apart and
converted to \code{while}-loop.
\code{while}-loop readily lends itself for `loop thinning' process, as one can
simply replace the keyword \code{while} with \code{if} at the proper time.


After `loop thinning',
aftermath changes may be performed for cleanup, convention conformation, or cosmetics.
Most importantly, following the removal of nested loops, other optimizations may become
accessible to further optimizations.
Like `Candy Crush Saga' game at a critical point, a single move may unlock a
gainful chain of reactivce moves.
This `avalanche effect' is the true value of the `loop thinning' technique.


Also note the application restrictions of the `loop thinning' process---inner loop must be directly
embedded in
outer loop with no intermediate layers;
also no bypassing statements, such as \code{break}, shall be in the pre-inner-loop section.


Most of the methods we present in this chapter are empirical, I cannot claim
universal applicability for many of them.
Instead, the techniques shall be considered on a case by case basis.
In what follows, we are going to demonstrate application of `loop thinning' technique through
a few examples adapted from real-world programming projects.

\section{Case Study: Quick Sort}\label{sec:nested-loop-quick-sort}

This is a classical example that was detailed by classical books such as `Programming
Pearls' and `Numerical Recipes'\cite{Bentley:1986:PP, NumericalRecipes:1992}.
It completely redefined what is simple code for me.


My first implementation of the quick sort algorithm was in C based off
the traditional `Hoare's partitioning' scheme, as presented
in `Numerical Recipes' (minus the sentinel part which is to be explained in
~\autoref{ch:sentinels}).


The entry point to the quick sort function is as follows.
\lstinputlisting[label={lst:QuickSortOutline},language=C,
caption={An implementation of quick sort algorithm.}]
{embedded-loops/quicksort_outline.c}
where the starting and ending pointers to the array are parameters to the partition function
`\code{part}'.
It is a recursive function whose base case is the no-op case---arrays with fewer
than two elements.
An array would undergo a series of partitioning operations until each partition is reduced to
base case at which point a final swap may be performed and the entire array is sorted.


It is critical to note that the partitioning function divide an array into three
parts---the left partition lesser or equal to the pivot element, the pivot element,
and the right partition greater or equal to the pivot element, in that order.
It may be the case that one or the other, but not both, of the left and right partitions is empty.
Finally a pointer pointing to the pivot element is returned.


With the Hoare's partitioning scheme, the function \code{part} in my implementation is as
follows.
\lstinputlisting[label={lst:nestedLoopHoareMethod},language=C,
caption={Implementation of Hoare's partition scheme for quick sort.}]
{embedded-loops/quicksort_partition_sym.c}
First, we randomly select a pivot element and swap it to the beginning of the array
(ask yourself: ``why beginning of array?
Why not end?'').
Then two pointers, \code{s} and \code{e}, start from the opposite ends of the array
and wade through the array to meet each other.
They stop at out-of-place elements.
When both stop, they swap out-of-place elements and back on the journey toward each other.
So on and so forth until they meet or cross.
At that point, the pivot element (at the beginning of the array) is swapped into its final position
and a pointer to this final position is returned.


The algorithm is straightforward to visualize but is actually tricky to implement.
So much so that once in a while it may take me a good two days to implement
a solution that passes a handful of basic test cases.
Among the frequently-made bugs in passing, a partial `gotcha' list is as follows:
\begin{enumerate}
    \item Pointers come to a stall
    %    \item Bug in pivot election (failed to swap)
    \item Bug in left pointer increment (each execution of the inner \code{while}-loop should
    cause at least one increment (decrement) operation unless boundary is met.)
    \item\label{itm:quicksort-boundary-condition} Incorrect boundary condition for pointer \code{e}
    (incorrectly set to \code{s < e}).
    \item Outer loop termination logic.
    \item Fail to swap the pivot element to its final position.
\end{enumerate}
In fact just to debug ~\autoref{itm:quicksort-boundary-condition} and
figure out the correct condition \code{pivot < e}, instead of \code{s < e}, took me $2$ hours.
Also, in the function \code{qsort}, the arguments to the recursive calls took a long time of
deliberation before I finally got them right.


To make the situation more complicated, different parts of the code are tightly
coupled---changing one would demand changes in other places.
For example, the returned pointer was switched among \code{s}, \code{s+1}, \code{e}, and
\code{e-1} multiple times.
Accompanying these changes, adjustments for the recursive calls are made from \code{qsort(s, p),
qsort(p, e)} to \code{qsort(s , p - 1), qsort(p, e)}, to \code{qsort(s, p + 1), qsort(p + 2, e)},
so on and on.
The number of combinations explodes.


This explains why it is so hard to implement this seemingly simple partitioning function correctly.
On the one hand, the problem itself is complicated---the number of loose parts exceeds what our
brain can comfortably handle at once.
On the other, however, the way we approach the problem exacerbates the
severity---we attempted to fight too many wars all at once.


Is there a more straightforward way to implement the quick sort algorithm?
Yes!
By dispatching two pointers both from the left end of the array,
one forerunner and one lagger, advancing at their own paces,
the Lomuto's partitioning scheme essentially simplifies the
partitioning scheme by fighting one war with one frontier.
The forefront pointer discovers and swaps out-of-place elements and the hind pointer guards
the boundary of partitions.
Notably, implementing this partitioning scheme only needs one loop as given below.
\lstinputlisting[label={lst:nestedLoopOnePointer},language=C,
caption={Implementation of partition function for Quicksort using one pointer.}]
{embedded-loops/quicksort_partition_asym.c}


It must be mentioned that the simplicity of this program comes with performance penalty
for certain cases,
One such case is a large array with many equal-valued elements where
the Lomuto's partitioning scheme would degrade to $O(N^2)$ runtime complexity (Can you figure out
why it is so?).
%\footnote{The reason is as follows.
%When faced with equal-valued elements, both ~\autoref{lst:nestedLoopHoareMethod}
%and ~\autoref{lst:nestedLoopOnePointer} still do pair-wise swap among two equal elements.
%But the ending position for the pivot element is seriously off to the right end of the array for
%Lomuto's partitioning scheme whereas that of the Hoare's ends up at the middle.}.
For this reason, Lomuto's partitioning scheme is not suitable for general-purpose libraries.


However, this code is still inspiring in both its simplicity and elegance while performing the same
task that a tricky, complicated program does.
Looking at ~\autoref{lst:nestedLoopHoareMethod} and the arduous debugging process to bring it about,
one can't help but thinking ``Wow!
A single loop takes the place of three nested loops.
What a simplification!''


Greedy developers cannot help but ask
``Can one implement quick sort with the simplicity but not the
performance degradation of Lomuto's?''
Now that we have the `loop thinning' technique in hand, we can give it try.
%The aforementioned loop thinning technique can be used to further simplify the Hoare's partitioning
%algorithm.
Starting with the implementation of Hoare's partitioning as ~\autoref{lst:nestedLoopHoareMethod},
let us see if there is a way to simplify the nested loops.
%a single-loop with cascade conditionals in the loop body
%(refer to ~\autoref{ch:conditional-cascade}).


The first encountered difficulty is the awkward conditional construct
in the densely packed inner loops:
\begin{lstlisting}
    while(s < e && *++s < *pivot);

\end{lstlisting}

loop state whenever the condition is tested.
Namely, each evaluation of the loop condition causes the pointers `\code{s}'
and `\code{e}' to advance.
If converted to conditional statements as is, it would not work as after certain conditions are
met, we need to hold the state and swap out-of-place elements.
But the program leaves us no chance to hold state.


So as a preparatory measure, we need to unfold the conditions of inner loops into
`normal' constructs before proceeding with other steps.
As we learned in ~\fullref{ch:loops}, these loops may be converted to
\code{do-while} loops such as
\lstinputlisting[language=C]{embedded-loops/quicksort_inner_loop_do_while.c}
and then to \code{while}-loop:
\lstinputlisting[language=C]{embedded-loops/quicksort_inner_loop_while.c}
After these changes, our the partition function becomes
\lstinputlisting[language=C]{embedded-loops/quicksort_partition_sym_expanded_inner_loop.c}
You may have noticed that we have floated ~\code{--e} up in front of the first inner loop,
and this does not affect the correctness as can be verified.


Now we can proceed with the second step
of loop thinning---move the pre-inner-loop statements out of the way with
`loop rotation' technique.
(``Loop rotation'' is specified in ~\fullref{sec:LoopDesignConsideration}.)
After this step, the code becomes:
\lstinputlisting[language=C]{embedded-loops/quicksort_partition_sym_rotated_inner_loop.c}
We have accelerated the process by tucking the post-inner-loop statements resulted from the loop
rotation to a conditional block.


Now we are ready with the third and most exciting step---converting inner loops to conditionals.
There is a minor complication we have not encountered so far:
we need to covert the second loop to an
`\code{else if}' clause of the first because the second inner loop is done after the first.
Our final result is posted below after the conversion:
\lstinputlisting[label={lst:nestedLoopHoarePartSingleLoop},language=C,

{embedded-loops/quicksort_partition_single_loop.c}
Note that we have combined multiple statements into a compound one `~\code{swap(s++, e--)}'.
By now we conclude our ``loop thinning' refactor process.


In retrospection, we set off to test the hypothetical quest for a simple but performant
partitioning scheme that comprises the advantages of Lomuto's and Hoare's partitioning scheme.
Comparing with where we started off ~\autoref{lst:nestedLoopHoareMethod},
we implemented the Hoare's algorithm with a single loop plus

In the process, we used the `loop rotation' techniques, the `loop thinning' techniques,

comparable simplicity as that of Lomuto's.
That's almost too good to be true!

As we can see the most fruitful software development model, undoubtedly, is to come up with a

In the course, one may discover new issues, adding new unit tests accordingly, and obtain new

With the variety of solutions passing the same unit tests, one can often form a better
perspective regarding the solution space.
This will help one pick the most effective solution to the original problem.

\section{Case Study: Search for Needle in Haystack Problem}\label{sec:nested-loop-pattern-matching}

For this case study, let us consider the `Search for a needle in a haystack' problem:
\begin{quote}
    ``Given two strings \code{needle} and \code{haystack}, search for the first occurrence of
    \code{needle} in the \code{haystack}.''
\end{quote}
There are many string matching algorithms with various run time complexities.
Some of them are simple to implement with quadratic runtime complexity.
Some else have superior runtime but require fairly sophisticated preprocessing,
such as Boyer–Moore algorithm
\footnote{\url{https://en.wikipedia.org/wiki/Boyer–Moore_string-search_algorithm}} and
Knuth–Morris–Pratt algorithm
\footnote{\url{https://en.wikipedia.org/wiki/Knuth–Morris–Pratt_algorithm}}.


In this section, we are going to leave these fancy algorithms and implementations but focus on
a rudimentary, naïve algorithm with a $O(MN)$ runtime.
The reasons are two-fold.
For one, this algorithm is the foundation of the more advanced algorithms.
For two, even this rudimentary algorithm takes considerable coding skills
out of a developer to correctly implement, and thus it makes a great example to illustrate
the various coding techniques we have presented so far.


The naïve algorithm is outlined as follows.
\begin{alisting}
    \caption{\label{alg:string-search-naive-algorithm}
    A naïve algorithm for string search whose runtime complexity is $O(MN)$ where $M$ and $N$ are
    the string lengths.}
    \begin{enumerate}
        \item For each index \code{i} in $[0, M-1]$, the index for the character array of
        the `\code{haystack}'
        \begin{enumerate}
            \item For each index \code{j} in $[0, N-1]$, the index for the
            character array of the `\code{needle}'
            \begin{enumerate}
                \item If characters at \code{i} and \code{j} do not match, break the inner loop
            \end{enumerate}
            \item If substring \code{s[i:i+j]} equals `\code{needle}', return \code{i}
        \end{enumerate}
        \item return -1
    \end{enumerate}
\end{alisting}


Let us start with a \java ~implementation with nested loops:
\lstinputlisting[label={lst:nestedLoop-string-search},caption={Code snippet with nested loops.}]
{embedded-loops/pattern_match_nested_loop.java}
We make this our starting point because it is the most commonly found
implementation of the algorithm.
If you have graded homework of college students or coding challenges from new graduates, chances
are that you will see something like this a lot in the submissions.


%Note that the abortion of the inner loop upon the first pair of mismatched
%characters is
%discovered or running out of character in \code{haystack}.
Before we apply the heavy-duty code simplification techniques, an insight for low-cost improvement
is that one can end the search of the `\code{needle}' when
the remaining part of the `\code{haystack}' is shorter than the `\code{needle}' to be searched.
With this change, the outer loop condition will become
\begin{lstlisting}
    i + needle.length() <= haystack.length()
\end{lstlisting}



An improvement on the inner loop can also be done---that is the awkward scope of the loop variable
\code{j}.
Currently its scope extends beyond the inner loop because its value is needed after the loop.
There are several options to resolve this awkwardness.
One is to use the `one-more-cycle' technique (see ~\pageref{sec:one-more-cycle} for more details).
Instead of terminating at $j = N$, let it terminate at $j = N+1$ so that a
iteration is dedicated to return successful search result.
Note that if done this way, the loop condition will be unnecessary as the loop is
either aborted in an earlier iteration or terminated on the $N+1$th iteration.
With these changes, the nested loop solution is shortened:
\lstinputlisting[label={lst:nestedLoop-one-more-cycle},caption={Code snippet with nested loops.}]
{embedded-loops/pattern_match_nested_loop_one_more_cycle.java}


We have so far gotten rid of the most commonly made implementation kinks.
%That is about what we can do with nested loops.
Even though we achieved simplification of a few lines, that is not all.
We can further simplify the implementation by doing away with the nested loop.


To that end, we will follow the prescriptions of `loop thinning' in
~\autoref{sec:loop-thinning-technique}.
Let us first prepare the code for the `loop thinning' process.
First off, let us convert all \code{for} loops to \code{while}-loops so as to reduce refactor
friction.
This implies that the increment statements, \code{++j} and \code{++j} are to be relocated to ends
of the corresponding loop bodies.


Then as usual, we eliminate the pre-inner-loop statements by `loop rotation'.
As a result, the initialization statement `\code{int j = 0}' is duplicated with one copy
at the forefront of the outer loop with the other after the last statement within the outer loop.
Also the inner loop now becomes an infinite loop \code{while(true)}.
If you are still with me, the code now looks like this:
\lstinputlisting[]{embedded-loops/pattern_match_thinning_loop_intermediate_stage.java}
It is important to note that this code still passes the same amount of
unit tests as ~\autoref{lst:nestedLoop-one-more-cycle} does.
This is the invariant that should be maintained at each important milestone
through a refactoring process.


Now we come to the second step of `loop thinning'.
Since the \code{break} statement in the inner loop is the only path that leads to the
execution of post-inner-loop statements, we can tuck them all under the same
conditional block wherein the \code{break} statement is.
Also, the condition for the same conditional statement is complementary to that of the
increment statement `\code{++j}', so we could shield \code{++j} in an \code{else} clause.


Hooray!
We are ready to remove the unconditional, inner loop---just strip it.
After this step, the code looks like this:
\lstinputlisting[]{embedded-loops/pattern_match_thinned_loop_intermediate_stage.java}
As a cleanup step if desired, the condition for the conditional statement with the
`\code{return}' statement may be merged into the loop condition.
The final version after this change is:
\lstinputlisting[label={lst:thinnedLoop},caption={Code snippet with nested loops.}]
{embedded-loops/pattern_match_thinned_loop.java}
Note that I have also switched the loop condition from
\begin{quote}
    \code{i + needle.length() <= haystack.length()}
\end{quote}
to
\begin{quote}
    \code{i + j < haystack.length()}
\end{quote}
without affecting correctness but made it more direct to ensure the safety of subsequent index
operation in the expression `\code{haystack.charAt(i + j)}'.

This completes the `loop thinning' process.
Looking back where we started, the latest version of implementation is both succinct and easier to
understand.


\section{Conclusion}\label{sec:loop-push-up-conclusion}

%What used to be one loop per data structure can actually be achieved with a one-layer loop plus
%cascade conditionals.


Nested loops are hard to understand and often pose obstacle to code refactor and extension.
%As can be seen, where nested loops occur are mostly related to dynamics adjustment to a
%streamlined processing code.
While compelling, many usages of nested loops can be
substituted with one simple loop and the resultant code is usually much simplified.
My advice is nested loops shall be avoided in production code.


The `loop thinning' technique makes a tunnel through which developers can overcome
refactor barriers to discover more interest implementations.
Even though the resulting solutions may not always be simpler, they often
offer valuable perspectives for inspiring better coding practices.
%Even if this is not possible or inconvenient, one can still boost the readability by
%factoring nested loops into more meaningful, reusable functions.
